# 通用
1. 生成提交日志时，必须使用下方「提交前缀规范」，以英文类型前缀开头、中文描述本次修改，禁止省略前缀。
2. 每次提交后请更新 `DEVELOPMENT_LOG.md` 文件（**必须严格按日期倒序排列，最新日期记录置于最上方，同一天记录聚合在同一日期标题下**）。
3. 每次大的变更请更新AGENTS.md文件
4. 默认不自动提交(git commit)，除非在提示词中明确要求提交。
5. **内置工具与文件检索规范**：阅读、分析和检索代码与项目文件时，必须优先使用内置专有工具（如 `view_file`、`grep_search`、`find_by_name`、`list_dir` 等），严禁随意通过终端执行 `Get-Content`、`cat`、`type`、`dir` 等 shell 命令读取文件。仅在执行项目构建、测试验证、Git 提交等必须依赖宿主环境的任务时才调用终端命令，避免触发多余的命令确认拦截。

# 提交前缀规范

1. 提交标题统一使用 `type: 中文说明` 或 `type(scope): 中文说明`。`type` 使用小写英文；`scope` 可选，填写本次修改的模块，如 `ai`、`mock`、`ci`，不允许空括号；冒号使用英文 `:`，后接一个空格。
2. 优先使用以下与 GitHub Actions 发布说明分组一致的类型：

   | 类型 | 用途 | 发布说明分组 |
   | --- | --- | --- |
   | `feat` | 新增功能 | Features |
   | `fix` | 修复问题（兼容历史 `bug` 前缀，新提交统一使用 `fix`） | Bug Fixes |
   | `opt` | 优化性能、交互或实现 | Optimizations |
   | `dep` | 依赖更新 | Dependencies |
   | `test` | 测试新增或调整 | Tests |
   | `docs` | 文档、使用指南或项目规则调整 | Documentation |

3. 其他类型（如 `chore`、`refactor`）仅在以上类型不适用时使用，发布时归入 Other Changes；无论使用哪种类型，都必须保留前缀。同一提交涉及多类修改时，按主要目的选择类型。
4. 提交前检查标题的类型、可选范围、英文冒号及中文说明是否完整。例如：`fix(ai): 修复日志筛选恢复问题`、`docs(mock): 完善使用指南`、`fix(ci): 修复发布说明分类`。不得使用 `修复日志筛选恢复问题` 等无前缀标题。

# 前端代码

1. 优先使用common-*等自定义组件
2. 修改前端js或vue等文件时使用eslint规则验证并通过后继续
3. 考虑代码支持国际化、黑白主题

# 后端代码

1. 优先使用已经存在的常量、枚举、工具类等
2. JDK版本是11，请使用11的语法特性，不要使用17及以上的语法特性
3. 优先使用MybatisPlus的查询方法，不要使用Mybatis的查询方法
