# 大文件导出与内存边界

导出接口保持原有 JSON 格式。原实现一次读取所有响应正文，再通过完整 JSON 缓冲、字符串和 UTF-8 字节数组写出，约 90 MiB 的数据可能同时存在多份副本。

新实现按 ID 游标逐条读取请求、响应数据、场景和 Schema，通过 Jackson 直接写入下载流，不再生成完整 JSON 字符串或字节数组。导出不加入事务，避免 MyBatis 会话缓存累积已导出的正文；历史请求与历史响应仍按原规则排除。场景、三层 Schema、日期和文本转义已与旧导出结构对比验证。

## 验证

可在仓库根目录运行定向测试：

```powershell
mvn -pl simple-boot-mock-server '-Dtest=MockGroupExportServiceTest' '-Dmock.export.large-test=true' '-DargLine=-Xmx512m' test
```

大数据测试使用临时 H2 磁盘库，两条响应正文分别为 40 MiB 和 50 MiB。数据准备在独立的 1 GiB 堆进程完成，随后在受限堆测试进程中导出，避免把 H2 写入巨型 VARCHAR 的峰值当作导出开销。测试读取导出文件，检查 JSON 结构和两条正文的完整长度。

2026-10-29：512 MiB Java 堆导出通过，输出 94,372,336 字节。该次导出测试进程的 Windows 峰值工作集约 624 MiB；这不是 512 MiB 容器内存验证，也不是完整线上应用的内存保证。

同一已有数据库在 256 MiB Java 堆下仍在 H2 SELECT 解码超大 VARCHAR 时发生 OOM，说明逐条导出不能消除数据库读取单条巨型字段的内存需求。

另以 1000 个请求和 1000 条小响应验证，导出通过，耗时约 12.282 秒、约 5N+3 次查询。该测试每次查询建立新连接，不能代表生产 Hikari 连接池或远端数据库的耗时。

## 运行边界

单条响应仍需由数据库驱动构造为 Java 对象，内存需求受最大单条正文、数据库缓存、并发和应用其他功能影响。H2 写入超大 VARCHAR 还会产生独立的缓冲开销。提高上传上限不能消除这些内存需求。

逐条读取降低正文累积，但增加查询次数；大量小记录的导出可能受数据库往返延迟影响。生产环境应结合实际数据库、完整应用和并发负载验证容量。
